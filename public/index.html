Browser Radio
for private communication

Radioteletype connects two users through WebRTC with live audio, video, chat, screen sharing, and direct file transfer.

Inspired by classic radioteletype and tactical communication terminals, built with modern
browser networking.
Purpose

Fast communication.
Minimal identity.

The goal is a stateless peer-to-peer communication experience: no accounts, no database, and no message history.

  • Users either join a known room or find another available peer.
  • The server only coordinates connection setup.
  • Media and files move directly between browsers.
  • The interface exposes connection status, channel state, and signal feedback.

WebSockets introduces peers.

WebRTC
carries data.

Radioteletype uses both because they solve different problems: one coordinates the connection, the other moves real-time media and data between browsers.

WebSocket A persistent browser-to-server connection. In this project it is the signaling line for room matching, offers, answers, and ICE candidates.
WebRTC A browser-to-browser real-time connection. It carries encrypted audio, video, chat, screen share, and X-FTP data channels.
Why both? Browsers need help finding each other first. After that, WebRTC can take over and avoid sending media through the backend.
Backend role The server stays lightweight: it coordinates setup, but it does not store accounts, messages, files, or call history.

Connection flow

Simple connection flow

The backend helps two browsers find each other. After the handshake, the session moves into WebRTC for real-time communication.

  • 1. Select A user chooses random matching or locks onto a private channel.
  • 2. Handshake WebSocket signaling exchanges offers, answers, and network candidates.
  • 3. Verify A short sync code lets both users confirm they are in the same secure session.
  • 4. Communicate Audio, video, chat, screen share, and X-FTP file data move through WebRTC.
Direct vs relay

STUN discovers.
TURN relays.

Direct Mode is preferred because media travels peer-to-peer. Relay Mode exists for networks where NAT or firewalls block that direct route.

VPS deployment

Self-hosted infrastructure
was part of
the work.

The project runs on a configured VPS using Nginx, PM2, HTTPS/WSS, and a coturn relay server for difficult networks.

  • Backend runtime Node + PM2 keep the signaling server running.
  • HTTPS/WSS Certbot and Let's Encrypt make browser camera, microphone, and WebSocket APIs work securely.
  • TURN relay turn.radioteletype.net:5349 uses TLS for Relay Mode when direct WebRTC fails.
  • Firewall control Relay traffic is limited to 49160-49200 on 87.106.194.178
    so the firewall only opens a small port range.

X-FTP file transfer

Chunked transfer.
Browser Blob.

X-FTP uses a dedicated ordered WebRTC DataChannel. The receiver accepts first, then the file is streamed in 32 KB pieces with progress and speed feedback.

Offer Sender shares filename, size, and MIME type. Receiver can accept, reject, or cancel.
→
Chunks The file is sliced into 32 KB chunks and sent in order.
32 KB 32 KB 32 KB 32 KB
→
Blob URL Received chunks stay in browser memory, then become a Blob/object URL for open or download.
  • Not permanent storage Files are not saved to a server. Object URLs are revoked when removed or when the page unloads.
